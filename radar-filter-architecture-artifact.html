Payload, Select2 e a decisão que o Radar tomou.

O Radar não segue o padrão nativo de filtros Blade+DataTable do Operações. Isso não foi acidente — foi resposta ao formato do produto. Esta página explica o porquê, o que funciona, o que pesa e para onde caminhamos.

O Radar filtra diferente. E isso tem motivo.

O Operações usa Blade + DataTable. O Radar usa Vue + JSON payloads. Entenda o que cada um faz e onde eles se cruzam.

Padrão nativo do Operações

Blade renderiza components.card.filter. Inputs viram filter-. DataTables serializa e o repository consome via withFilter($request).

Permission-aware dropdowns são pré-limitados por PermissionHelper e filter-limit. Place::scopeWithFilter() cobre a maioria dos campos.

Padrão do Radar

Um mount point Blade entrega URLs ao <radar-app>. O RadarFilterBar.vue monta os controles. O Vuex envia query params para endpoints JSON.

O RadarController responde com envelope {response, status, message, options}. O RadarRepository aplica escopo + filtros direto no query builder.

Um filtro, cinco superfícies.

O mesmo estado de filtro alimenta equipamentos, mapa, dashboard, detalhe e opções. Clique nas abas para ver como cada endpoint consome o payload.

Lista de equipamentos

Recebe todos os 13 filtros. Retorna cards paginados com dados do place, mídia e ações. Cache key inclui scope + filters + page.

Query

baseScopedPlaceQuery() -> applySystemScope() -> applyCspScope() -> applyUserFilters(request) -> paginate()

Payload

{ "search": "av paulista", "establishment_id": [1,3], "squares": ["SP-1"], "active": "1", "commercialized": "all" }

Paginado

O único endpoint que usa paginação clássica. Mapa e dashboard não paginam — eles agregam ou amostram.

Markers do mapa

Recebe filtros, retorna array de markers com lat/lng. Tem limite máximo de markers e enquadramento visual para escopos amplos. Cache key é diferente do equipamento porque o payload shape é diferente.

Quando o escopo é nacional ou multi-concessão, o mapa enquadra o viewport sem inflar o payload — o framing é frontend.

Não é DataTable

Mapa não tem recordsTotal, recordsFiltered, start, length. O contrato é outro: markers com coordenadas + dados resumidos para popup.

Dashboard agregado

KPIs, charts e insights agregados por concessão. Não retorna rows individuais — retorna contagens, distribuições e tendências.

O JSON público esconde arrays internos de IDs. O resource remove establishment_ids e excluded_establishment_ids antes de serializar.

Stale-while-refresh

Endpoints pesados podem servir o último payload válido enquanto um request atualiza. Em cold cache, o lock tem espera curta e fallback limitado.

Opções de filtro dinâmicas

O endpoint filter-options recomputa cada lista de opções a partir do universo já filtrado, excluindo o próprio campo.

Exemplo: a lista de Praças respeita estabelecimento, filial, status, etc. — mas ignora a Praça selecionada para não prender o dropdown.

Por que dinâmico?

Opções estáticas do Blade são simples para listas CRUD. O Radar precisa que cada dropdown reflita o que ainda existe dentro do escopo autorizado + filtros ativos.

A fronteira que request filters não atravessam.

Filtros de request só estreitam. Nunca ampliam. A autorização é tripla: config Radar, permissões vivas e filtros do usuário.

Por que payload, e não Blade?

Radar não é uma listagem CRUD. É um módulo multi-superfície com mapa, dashboard, cache pesado e UX interativa.

1. Radar não é uma lista só
Tem cards, mapa, dashboard, detalhe e opções. DataTable resolve só a lista.
formato
2. Cada endpoint precisa de shape diferente
recordsTotal/recordsFiltered não serve para markers ou KPIs agregados.
contrato
3. Cache key precisa de contexto completo
radarCacheKey() hasheia scope + filters + payload. DataTable não tem esse conceito.
cache
4. Stale-request cancellation
Vuex cancela Axios calls antigas. Blade form submit não tem esse controle.
frontend
5. Filtros cross-filtered
Dropdowns atualizam contra o universo filtrado. Blade static options são mais simples, mas não servem.
UX
6. Mapa é stateful
Max markers, framing de escopo amplo, balanceamento multi-square. Não mapeia para pipeline de tabela.
mapa

O lado bom e o lado que pesa.

Nenhuma decisão de arquitetura é grátis. A payload-driven filtering resolve problemas reais, mas traz custos.

O que funciona bem

  • Um filtro state dirige equipamento, dashboard e mapa consistentemente.
  • Filtros normalizados em arrays determinísticos = cache keys estáveis.
  • Cache pesado inclui scope e contexto de filtro, reduzindo risco de leak.
  • Dropdowns se adaptam ao resultado ativo — usuário vê só o que existe.
  • Vuex cancellation evita que resposta antiga sobrescreva filtro novo.
  • Cada endpoint devolve o shape que precisa, sem forçar contrato de DataTable.
  • Fronteira de permissão é explícita e coberta por RadarScopeBoundaryTest.

O que pesa

  • Parece não-nativo dentro do Operações porque bypassa o fluxo Blade+DataTable.
  • Vocabulário duplicado: branch_ids vs shelter_model_id (Radar) vs shelter_model_ids (Place).
  • Filtros Radar-only (panel, facility, with_photo) não existem no Place filter scope.
  • Filtragem de permissão reimplementada no RadarRepository em vez de reusar fluxo de Pontos.
  • Correção do cache depende de lembrar cada key em activeFilters() e radarCacheKey().
  • Vue/Select2 state é mais complexo que form state Blade, com lifecycle e stale-request manual.
  • Qualquer rename futuro toca Vue, Vuex, repository, cache, resources e testes.

O Select2 saiu do FilterBar e virou componente.

A extração reduziu duplicação sem mexer no Select2 compartilhado do Operações.

Antes: tudo inline

O RadarFilterBar.vue importava jQuery e Select2 diretamente. Tinha init, destroy, sync de valor, sync de disabled, controle de pending multi-select e reopen — tudo na mão.

Imports duplicados

import $ from 'jquery' import 'select2' // + 120 linhas de lifecycle // manual do plugin

Riscos

- destroyed() em vez de beforeUnmount - pending keys manual - sync reemite mudança? - destroy limpa tudo?

Agora: RadarSelect2

O RadarSelect2.vue encapsula todo o lifecycle do plugin jQuery/Select2. O FilterBar foca em lógica de domínio.

Props

modelValue, options, multiple, placeholder, disabled, loading, staticOptions, valueKey, labelKey

Emits

update:modelValue → sempre apply → single: imediato → multi: só no close → nunca por sync interno
antes

FilterBar com jQuery inline

Import direto. Init/destroy manual. Pending keys. Sync reemite ou não? Reopen manual.

agora

FilterBar + RadarSelect2

FilterBar foca em domínio: debounce, active count, clear all, filters-changed. RadarSelect2 cuida do plugin.

Contrato do RadarSelect2 (clique para expandir)
  • Single-select: aplica imediatamente. Emite apply no change.
  • Multi-select: atualiza state local enquanto aberto. Reopen no select/unselect. Emite apply só no close.
  • Disabled: prop disabled ou loading desativam o controle.
  • Locked: FilterBar decide. Se options vazio, renderiza disabled.
  • Clear all: FilterBar reseta valores e emite um payload vazio.
  • Lifecycle: Vue 3 (mounted + beforeUnmount), não destroyed.
  • Namespacing: eventos jQuery usam .radar para não conflitar.
  • Select2.vue compartilhado: não foi alterado.

O caminho para mais perto do nativo.

Não é trocar tudo. É normalizar o que dá e manter o que o Radar precisa.

Rota híbrida: manter payloads, alinhar vocabulário.

A recomendação não é substituir o Radar por DataTable wholesale. É normalizar a camada de filtro com o vocabulário nativo enquanto mantém os endpoints específicos.

1. Inventário

Mapear chaves Radar para chaves Place. Backend normaliza aliases internamente.

2. Normalizador

RadarFilterRequestNormalizer: converte aliases, dropa transport params, separa place/radar filters.

3. Reuso

Refatorar filteredPlaceQuery() para chamar Place::withFilter() no subset comum.

4. Decisão

Conservador: normalizar server-side. Ou: migrar Vue para plurais nativos com janela de deprecation.

Comparação: conservador vs. limpo
conservador

Manter keys Vue

Backend normaliza para sempre. Menor risco imediato. Zero mudança no frontend.

limpo

Migrar para plurais nativos

Vue passa a enviar establishment_ids, shelter_model_ids. Bump no cache namespace. Testes cobrem aliases antigos por um tempo.

Para PR #876, conservador é mais seguro. Migrar keys pode ser Phase 2.

Posição final

Payload-driven filtering não é automaticamente ruim aqui. É uma resposta razoável ao formato multi-view, cache-heavy e interativo do Radar. O ponto fraco não é "payloads existem" — é que o Radar normaliza e nomeia filtros demais em vez de ficar mais perto do vocabulário nativo do Place.

híbrido é o melhor caminho
