A virada foi separar o que parecia uma coisa só.

O Radar tinha três dimensões misturadas: permissão de tela, escopo operacional de pontos e estratégia de cache. A rodada final tornou essas fronteiras explícitas.

01

Permissão não é escopo.

radar-* decide se o usuário pode abrir uma view ou endpoint. pontos-menu decide quais dados operacionais ele pode enxergar.

02

Cache visível é o cache web.

Depois da confirmação Labs/Jobs, comandos Artisan deixaram de ser resposta operacional para o cache que o usuário vê.

03

Frontend recebe capacidades, não adivinha.

O Blade entrega só as rotas autorizadas. Map-only carrega mapa sem tentar dashboard.

O resolver extra saiu do caminho.

O RadarScopeResolver foi removido porque duplicava a leitura de filtros que o Operações já centraliza em PermissionHelper.

removido

app/Services/Radar/RadarScopeResolver.php

O que fazia

Reabria filtros de perfil/usuário, aliases e fallback global para responder se o usuário tinha escopo Radar.

Por que saiu

Virou um segundo parser de permissões ao lado do parser real do sistema.

mantido

UserPolicy alias-only

Sintaxe

$user->can('radar-mapa')

Serve para

Decidir se pode abrir view/endpoint: equipamentos, dashboard ou mapa.

reposicionado

RadarRepository + PermissionHelper

Sintaxe

PermissionHelper::getByProperty('pontos-menu', 'squares')

Serve para

Resolver escopo de dados e aplicar config ∩ pontos-menu ∩ request filters.

Endpoint autorizado

Policy só responde a pergunta de acesso.

@can('radar-mapa') rota /radar/map existe para o usuário @endcan

Dados autorizados

Repository resolve a pergunta de escopo.

base Radar config ∩ pontos-menu via PermissionHelper ∩ filtros da request = payload permitido

Escopo voltou para o lugar certo.

O RadarScopeResolver foi removido. O UserPolicy ficou alias-only para permissões Radar. O escopo de dados voltou para RadarRepository, usando os filtros vivos de pontos-menu via PermissionHelper.

antes do hardening

Risco

Usuário com Radar, mas sem escopo vivo de pontos, podia cair em fallback de concessão ativa e receber SP.

agora

Contrato

Sem pontos-menu vivo, endpoints autorizados retornam payload vazio. Sem permissão do endpoint, continuam 403.

Mapa nacional ficou mais honesto.

O centro do mapa vem das praças autorizadas, pontos inválidos/fora do Brasil são ignorados, e escopos amplos são enquadrados visualmente sem inflar o payload.

Sem superfície Artisan Radar.

Os comandos radar:cache:* e radar:health foram removidos para não vender uma operação que pode aquecer o servidor errado quando Jobs e Labs não compartilham cache.

Cache agora segue o caminho real do usuário.

1. filtros

Primeiro carrega opções permitidas.

2. dashboard

Prefetch só se a rota existir.

3. mapa

Mapa espera a sequência segura.

4. stale

Payload pesado pode servir dado stale durante refresh.

Map-only deixou de pagar pelo dashboard.

O payload do radar-app agora é montado por capacidade explícita: map-only recebe map e filterOptions, mas não recebe URL de dashboard.

Sequência continua segura para request stale.

As ações Vuex mantêm cancelamento/request-id para não continuar um fluxo antigo. Usuário com dashboard ainda preserva o prefetch de cold-cache.

IDs internos saíram do JSON público.

O dashboard preserva cache key e query scope internos, mas o resource remove filters.scope.establishment_ids e excluded_establishment_ids da resposta pública.

Metadados úteis continuam.

A resposta pode seguir expondo chave/label de concessão, praça, cidade e UF. O que saiu foi detalhe bruto de autorização.

Exemplos de comportamento esperado.

Estes são os cenários que reduzem o risco de review: endpoint permitido carrega, endpoint negado responde 403, filtro de request nunca amplia escopo.

map-only

Usuário com radar-mapa, sem radar-dashboard

  • /radar/map: 200.
  • /radar/data/filter-options: 200.
  • /radar/data/map?limit=1: 200.
  • /radar/data/dashboard: 403.
  • HTML não entrega rota de dashboard ao Vue.
Radar sem pontos-menu

Usuário tem Radar, mas não tem escopo operacional vivo

  • Equipamentos, mapa, dashboard e filtros autorizados retornam payload vazio.
  • Não há fallback para active_concession=sp.
  • Permissão faltante de endpoint continua 403.
dashboard

Usuário com dashboard autorizado

  • Recebe rota de dashboard no Blade.
  • Map load pode fazer prefetch de dashboard.
  • Cache pesado pode responder stale enquanto um refresh acontece.
  • JSON público não vaza arrays internos de IDs.
